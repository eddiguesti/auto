# Native Cloudflare API

`../api-staging.js` runs the native D1/R2/Queues/Durable Objects implementation. The selected release starts with an empty database, as requested; the offline Railway database and old accounts are not imported or deleted. All new timestamp writes use UTC. Historical data-import tools remain available separately.

`wrangler.api-staging.jsonc` targets the new **easy Memoir** account (`bbdbba416f07c76f4c2754f8a61807f4`) and real isolated `easy-memoir-staging` D1 database. The API has no public routes, workers.dev endpoint or preview URL. `../wrangler.web-staging.jsonc` exposes assets and forwards `/api` and `/api/v1` to it through an `API` service binding. Always select an explicit staging config and the `easy-memoir` Wrangler profile; the default frontend config names a separate future production service.

## Runtime contracts

Both API prefixes preserve private/no-store responses, authenticated ownership and immediate session revocation. Native modules implement:

| Area       | Modules and behavior                                                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts   | Password/Google login, registration, verification/resend, password recovery, profile/settings, complete export and atomic account erasure.           |
| Writing    | Stories, standalone memories, memos, chapter review/edit/rewrite, AI assistance, checkpointed style jobs and canonical manuscripts.                  |
| Media      | Private photos, recording uploads/transcription, chapter artwork, cover metadata and durable orphan cleanup.                                         |
| Voice      | Single-use browser WebSocket tickets, scoped magic conversations, raw transcript acknowledgement, compilation jobs and phone interview coordination. |
| Publishing | Durable EPUB/audiobook generation, owner status/download, paid checkout receipts, signed Stripe webhooks, print proofs and Bookvault dispatch.       |
| Progress   | Daily prompts, collections, achievements, streaks, circles and family encouragement.                                                                 |

Provider configuration and hosted acceptance remain separate from local tests. `PUBLISHING_ENABLED`, print fulfilment, phone calls/callback acceptance and notification delivery stay disabled until configured and accepted. The public catalog reports checkout unavailable when required gates or provider configuration are missing. No unavailable workflow claims to have completed a paid generation, delivery or physical order. New recurring subscriptions remain disabled.

`GET /health` reports staging status and `productionReady:false`. Scheduled task attempts/successes are persisted separately in `cron_health`; independent tasks still run when another fails, and the event reports failure without exposing provider messages. A successful basic health response does not establish provider or production readiness. Unported endpoints return explicit errors.

## Authentication and stored values

- Password hashing retains bcrypt12 using the browser-compatible bundle and Web Crypto. This exceeds Workers Free's CPU allowance; the API requests a 5-second CPU budget and needs Workers Paid plus hosted profiling. Local wall time is not hosted CPU evidence.
- The fresh workers.dev deployment explicitly uses `AUTH_RATE_MODE=account-budget`: atomic D1 global and normalized-account limits, bounded public bodies and fail-closed database handling. It trusts no forwarded IP headers. See [AUTH_BUDGET.md](../AUTH_BUDGET.md). The separate signed-ingress option is documented in [INGRESS.md](../INGRESS.md) and requires its own verified custom-domain policy before use.
- HS256 tokens require canonical encoding, integer owner/issue/expiry claims and authoritative revocation checks in a `first-primary` D1 session. Scoped magic tokens cannot access generic account, writing or billing endpoints. Browser voice URLs contain short-lived single-use tickets, never account JWTs.
- Resend delivery requires a configured verified sender and `APP_URL`; unavailable delivery never pretends to succeed. Google login requires matching frontend/backend client IDs and the deployed origin authorized in Google Console. See [NATIVE_AUTH_VOICE.md](../NATIVE_AUTH_VOICE.md).
- D1 stores JSON as validated text, nullable booleans as NULL/0/1, exact decimals as text, and timestamps according to the reviewed mapping. API conversion rejects invalid or lossy values. The explicit UTC policy here concerns fresh native writes; importing old data still needs independent source-timezone evidence.
- Story mutations atomically store their outbox intent and invalidate stale compiled/reviewed derivatives. Queue effects use durable fenced claims; ambiguous paid provider requests pause for reconciliation instead of automatically buying the same work again.
- Account erasure atomically records private-media cleanup and removes owned content. In-flight print/financial/delivery operations guard erasure at the database transaction boundary. Phone hangup controls are reserved before owner erasure, and media still being uploaded retains a bounded cleanup grace.

## Complete account export and edited manuscript state

`GET /user/export-data` streams all 39 owned data groups in the current Node account-export contract plus 21 native groups for saved story/style snapshots, artwork prompts, generation/print/checkout state, voice compilation, game receipts, phone transcript history, safe notification metadata, Telegram history and verified-email newsletter records. Every group is an array of mapped rows, including final chapter reviews, standalone stories, memos, uploaded recordings, voice sessions, calls, print orders, payment history and notifications. Password hashes, authentication tokens, internal leases/mutation claims, nonce hashes, active link codes and encrypted provider delivery envelopes remain excluded. Notification bodies use safe plaintext renditions with bearer URLs omitted; native delivery metadata complements that history. Newsletter rows are included only when the account has verified control of the matching email address. Explicit photo ownership takes precedence over an inconsistent story link; legacy photos without an owner inherit the linked story owner. No other owner's story fields are joined into photo metadata.

The response is one JSON document with `exportComplete:true` only at its end. Clients must consume valid JSON and require that completion marker before offering a completed download. All group high-water keys are captured in one authorized batch, followed by uniquely ordered keyset pages (including composite history keys) of at most 100 records. SQL applies a conservative 1 MiB escaped-JSON page budget before rows reach the Worker; a larger single row is emitted alone. There is no total-record truncation. Dates, JSON and nullable booleans use the same reviewed codecs as other native routes.

Each page uses a fresh `first-primary` D1 session and batches current account/token checks with its data read. Deletion, expiry, logout, user-wide revocation or a database failure interrupts the body rather than closing valid partial JSON. Export is explicitly **not** a point-in-time snapshot: records may be edited or removed between pages, and rows beyond a group's captured high-water key are excluded. Concurrent insertions within the captured key range (including random UUID keys) may appear or be skipped; the boundary is a key range, not a creation-time snapshot. For a durable immutable snapshot across a long export, a separate background snapshot workflow is still required.

D1 itself limits table rows/values to 2,000,000 bytes and binding calls per invocation; exports that hit a hosted runtime/query limit fail rather than silently omit data. Very large accounts may need a resumable R2-backed export workflow. These are platform ceilings, not application record caps. See [current D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

Raw story edits clear `compiled_content` and `compiled_at` in the same transaction as the new answer and durable outbox event. Reviewed chapter text is retained; its older `updated_at` makes canonical publishing reject a stale review until the author reviews the latest answers. Settings reads are authoritative, and author-name changes do not erase compiled or reviewed chapter content.

## Offline verification

```powershell
npm run test:cloudflare:api
npm run check:cloudflare:api
```

The tests build actual Workers, start workerd through the installed Miniflare, create real local D1 tables from the audited schema, and execute HTTP requests and repository statements. Auth tests cover browser bcrypt compatibility, native JWT minting accepted by Node, public-route validation, duplicate/concurrent registration, real game-state transaction rollback, atomic rate windows, trusted-provider privacy/failure, email-provider failure and one-time verification rollback. Story tests cover owner isolation, both prefixes, JWT signature/expiry, premium gates, real transaction rollback, concurrent upserts, exact imported date storage, scoped access, immediate logout, fingerprint logout and fail-closed revocation outages. They use synthetic local accounts and test secrets; no live source data, remote resources or DNS are touched.

For a new environment, initialize the reviewed `../db/schema.sql` with the guarded fresh-database initializer, then apply every frozen native migration in order. Seed the static game catalog using `tools/scripts/cloudflare-game-seed.mjs`; it contains no account data. Supply secrets using Wrangler secret commands and private R2 objects using the correct explicit account/profile. Activate R2 and Workers Paid in the dashboard before deploying this complete configuration. Never reset an existing database to rerun initialization. See [db/README.md](../db/README.md) for initializer/importer safety and verification receipts.

Hosted checks must cover the real frontend→service binding→D1/R2 flow, bcrypt CPU, queue/cron execution, WebSocket upgrades, deployed OAuth origins, signed callbacks and provider configuration. Local tests use fake provider transports and synthetic accounts; they do not attest to actual emails, phone audio, payments or printer delivery.

References: [D1 batches and sessions](https://developers.cloudflare.com/d1/worker-api/d1-database/), [local D1 testing](https://developers.cloudflare.com/d1/best-practices/local-development/), [bcryptjs browser/WebCrypto implementation](https://github.com/dcodeIO/bcrypt.js/blob/main/README.md), [Worker CPU limits](https://developers.cloudflare.com/workers/platform/limits/), [Cloudflare IP-header/subrequest behavior](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

## Native writing and canonical publishing

`writing.js` handles the existing standalone-story and memo CRUD contracts, chapter review GET/manual save/rewrite/Clio edit, `/ai/interview`, `/ai/write-story`, `/ai/chat`, illustration-prompt generation, style preferences/preview/revert, and the unpaid `/export/manuscript` preview. These routes require full account credentials. All SQL ownership predicates include the authenticated account; private recording references must belong to that account. Text-only memos are supported. Ordinary reads, manual saves and metadata operations do not consume AI quota.

`writing-manuscript.js` is shared with every native publisher. Saved reviewed chapter text overrides individual answers; unreviewed chapters use their saved answers. Voice `compiled_content` remains an auxiliary summary and does not replace the author's answer. Standalone memories appear under “Other Memories”. Changed or deleted source answers invalidate the corresponding review rather than silently publishing stale copy. Photo joins exclude inconsistent explicit owners. Canonical assembly has an explicit 8 MiB aggregate memory boundary; it returns `MANUSCRIPT_TOO_LARGE` instead of truncating. Complete account export remains available separately.

`writing-provider.js` uses direct bounded fetch to the fixed xAI Responses endpoint, `store:false`, a 60-second deadline, a 1 MiB response limit and complete-output validation. `GROK_MODEL` defaults to the currently documented `grok-4.7`. Older Grok 4.1 text model IDs were retired; photo analysis uses the same current provider helper. Each paid action reserves the shared atomic daily AI quota and a per-account writing rate window. No automatic provider retry can silently rebill an ambiguous request. See the [current xAI model catalog](https://docs.x.ai/developers/models) and [Responses documentation](https://docs.x.ai/developers/model-capabilities/text/generate-text).

Style apply-all now returns `202 {jobId,...}`. Migration `0006_writing.sql` and the generation Queue consumer checkpoint the full owner source set, process at most three memories per delivery, and preserve each original answer. Updates compare the original answer/version and the current job lease inside the write transaction. A newer author edit is retained and reported as `SOURCE_CHANGED`. A failed or unconfirmed paid effect stops for reconciliation and is never automatically replayed. Revert atomically cancels a live style job before restoring originals. Account deletion cascades through all copied source checkpoints. `GET /style/jobs/:jobId` returns owner-only status, transformed/total counts and any per-story conflicts. The web UI resumes saved jobs, supports leaving the page during processing, and accepts both queued EPUB downloads and legacy immediate EPUB binaries.

Regression coverage uses actual Miniflare/workerd D1 and R2, replacing only external provider transport. It covers ownership, all author edit paths, source changes during provider calls, provider failure/incomplete/oversized responses, concurrent quota limits, bounded style continuation, duplicate Queue delivery, revert and account-deletion fencing.

## Native print proofs and physical orders

`print.js` implements the current `/print/status`, `/print/proof`, private PDF proof and approval contracts. The package remains ten A5 matte hardbacks for £250, at most 200 pages and eight colour photo pages, with delivery to one GB or FR address. Proofs use the same canonical manuscript as electronic publishing. The native PDF layout follows the existing `memoirPrintPdf.js` layout and embeds the licensed NotoSerif font. Seed the exact checked-in font into private R2 at `assets/fonts/NotoSerif-Regular.ttf`; the Worker verifies SHA-256 `c8f669ceb2c9c60ccf55198b305e08a997ffca79a38cc7eeb551e643cbe66505` before use. The original font and OFL notice remain under `services/api/assets/fonts`.

Proofs require an unused paid print entitlement, and approval atomically reserves that entitlement with a durable dispatch/outbox record. Competing approvals cannot spend the same entitlement. Immutable proof objects have cleanup intent before either R2 write. Only the owning account can view an unapproved proof. Approved printer downloads use narrowly scoped HMAC capability URLs for exactly one order/file type and at most seven days; these routes also recheck the active owner and paid entitlement. No account bearer token appears in these URLs.

`PRINT_QUEUE` runs `consumePrintQueue`; the scheduled publisher calls `publishPrintOutbox`. Bookvault requests use the fixed v4 origin, bounded responses, explicit deadlines and manual redirect rejection. The current official [Bookvault v4 schema](https://api.bookvault.app/swagger/docs/v4) was checked for title calculation, transient SKUs and order/DocRef lookup. Every order uses `EM-<order UUID>` as its stable DocRef. A paid POST boundary commits before submission. A lost response is reconciled by DocRef; an unresolved acceptance pauses for review and is never automatically POSTed a second time. Tracking polls update the same immutable order. Migration `0009_print_artwork.sql` also prevents account erasure from racing a queued or unresolved physical order.

`PRINT_CONFIGURATION_READY` and `PRINT_FULFILMENT_ENABLED` remain false until real merchant configuration and fulfilment acceptance are verified. Required settings are `BOOKVAULT_API_KEY`, text/cover stock IDs, a positive French declared shipment value, a public HTTPS API origin and a signing secret of at least 32 characters. Merely supplying an API key does not enable sales. French shipments retain DDP and the configured declared value. Selected photographs are bounded to 16 MiB compressed in aggregate, four megapixels per PNG and eight megapixels across PNGs to keep PDF decoding inside Worker memory. Larger photographs must be resized or supplied as JPEGs; no image or manuscript is silently omitted.

## Private chapter artwork and covers

`artwork.js` preserves owner-scoped cover metadata and chapter-image list/status/generate/reset contracts. Structured cover settings round-trip as JSON. The cover options describe the current ten-book package rather than historical Lulu prices. Chapter images use private R2 URLs served only to their owner. The optional onboarding callback enqueues only the initial chapter; onboarding details remain saved if artwork is unavailable.

`ARTWORK_QUEUE` runs `consumeArtworkQueue`, and the scheduled publisher calls `publishArtworkOutbox`. One paid xAI Imagine request is recorded before the call; its deferred request ID is persisted and resumed through safe polling. Polling and downloads do not charge another daily AI request. Only the documented `imgen.x.ai` ephemeral image origin is accepted, with no redirect or authorization header. See [current image generation](https://docs.x.ai/developers/model-capabilities/images/generation) and [Imagine output locations](https://docs.x.ai/developers/model-capabilities/imagine/files/outputs). Provider envelopes are bounded, binary signatures are checked, and the download limit is 8 MiB. Private completed images replace old images only after a fenced D1 commit.

Each artwork processing claim writes an independent immutable R2 object. A late write from an expired claim cannot replace a newer completed image. Cleanup intents survive account deletion, resets and partial object writes; the one-hour grace exceeds the documented [15-minute Queue consumer wall time](https://developers.cloudflare.com/queues/platform/limits/). A lost initial provider response pauses for review rather than buying another image automatically. Regeneration and reset schedule superseded private assets for removal.
